Design note

Handling Ambiguous Payment Outcomes

Ian Mark Ganut · November 2026

Context

At a previous fintech I owned the services that originated ACH debits for mortgages and loans, including a text-to-pay API. We submitted every debit through our ODFI’s API.

The most expensive class of bug was never a crash. It was the case where every system did exactly what it was told and the books still did not balance.

The incident

A customer initiated a payment of roughly $1,250. We created one payment record and called the ODFI API. The call timed out after the ODFI had already accepted the entry. Retry logic generated a second internal ID and submitted another debit. Both entries settled. Two days later the settlement file showed two debits; our ledger contained only one SUCCESS row.

The original payment was legitimate and correctly remained SUCCESS. The second debit had never been recorded on our side, so it appeared as an unmatched settlement. Cash was over by the full amount. That excess belonged to the customer and sat as a liability until returned.

Ledger entries

AccountDebitCredit
Cashamount—

Reversing entry within the five-banking-day NACHA window
AccountDebitCredit
Owed to Customeramount—
Cash—amount

We discovered the issue only when the customer called. At the time we had no automated daily match against the ODFI settlement file.

Design principles that came out of it

  1. A timeout or missing acknowledgment is not a failure. It is an unknown outcome.
  2. The original legitimate payment must stay SUCCESS. A new record is created for any unmatched settlement.
  3. Idempotency keys must be generated before the external call and must be stable across retries. For text-to-pay we built the key from the payment-request ID created on the first text, plus statement ID and amount. A second text for the same statement produced the same key and was rejected.
  4. The settlement file (or carrier invoice) is the source of truth. Reconciliation creates the liability and posts the correcting transaction; it does not edit the original row.
  5. Reversals are preferred inside the NACHA window; after that window a new credit is issued.

Recommended state handling

PENDING ├─→ SUCCESS (acknowledgment received) └─→ OUTCOME_UNKNOWN (timeout / no response) └─→ RECONCILING (settlement match runs) ├─→ MATCHED └─→ UNMATCHED → create liability → REVERSED or REFUNDED

The original payment row is never moved to REVERSED. Only the newly created liability record is.

Mapping to label purchase

Buying a carrier label is the same shape of problem: an external charge that can succeed even when the response is lost. The same rules apply:

  • Treat a timeout as OUTCOME_UNKNOWN, not FAILED.
  • Keep a stable request ID across retries.
  • Make the carrier invoice the source of truth.
  • Create a correcting transaction for any unmatched charge rather than mutating the original purchase record.
  • Place the label purchase at the saga pivot: everything before it is compensatable, everything after it is retry-only or reconciled.

This pattern is why I now start every payment or money-adjacent design from the ambiguous case instead of the happy path.
