Design note

Handling Ambiguous Payment Outcomes

Ian Mark Ganut · November 2026

Context

I owned the services that originated ACH debits for mortgages and loans, including a text-to-pay API. This is the failure mode I design against.

The most expensive class of payment bug is rarely a crash. It’s the case where every system does exactly what it was told and the books still don’t balance. The usual cause is one assumption: that “I didn’t get a response” means “the money didn’t move.”

A worked scenario

Details and numbers are illustrative; the failure mode is real.

Consider an ACH debit for $1,250.00. The service creates one payment record, marks it PENDING, and calls the bank’s API. The bank accepts the entry, but the response never arrives, and the call times out.

Suppose the retry logic treats the timeout as a failure and submits again with a new internal ID. Without a shared idempotency key, the bank has no way to know the two requests are the same payment, so it accepts both. The retry’s response arrives and the payment record is updated with the retry’s ID. The record now reflects the retry; the original submission is the orphan. Two days later:

SourceWhat it shows
Our ledgerOne payment, SUCCESS, $1,250.00
Bank settlement fileTwo settled debits, $1,250.00 each
Customer’s bank statementDebited twice

Every component behaved correctly in isolation. The payment record is legitimate and should stay SUCCESS. The original submission has no record on our side, so its settlement is unmatched, and cash is over by $1,250.00. That money belongs to the customer, so it is a liability until it goes back.

Without a daily match against the settlement file, the first signal is the customer calling support. With one, the unmatched debit surfaces the morning the file arrives.

Ledger entries

Recording the unmatched debit:

DebitCreditAmount
CashOwed to customer$1,250.00

Returning it with a reversing entry inside the NACHA window (after the window, a new ACH credit):

DebitCreditAmount
Owed to customerCash$1,250.00

Both entries balance, and neither touches the original payment. The correction is new history, not an edit of old history.

How it was fixed

In the real incident, the issue surfaced only when the customer called. At the time there was no automated daily match against the ODFI settlement file. The fix had three parts:

  1. Return the customer’s money. The duplicate debit was recorded as a liability and returned with a reversing entry inside the five-banking-day NACHA window. The original payment stayed SUCCESS throughout.
  2. Make retries safe. The idempotency key is now generated before the external call and stays stable across retries. For text-to-pay, it is built from the payment-request ID created on the first text, plus the statement ID and amount. A second text for the same statement produces the same key and is rejected.
  3. Reconcile daily. A missing response is treated as OUTCOME_UNKNOWN and resolved against the settlement file, so an unmatched debit surfaces the morning the file arrives instead of when the customer calls.

Design principles that came out of it

  1. A timeout or missing acknowledgment is an unknown outcome, not a failure.
  2. The original legitimate payment stays SUCCESS. Any unmatched settlement gets a new record.
  3. Idempotency keys are generated before the external call and stay stable across retries. For text-to-pay, derive the key from the payment-request ID created by the first text, the statement ID and the amount, so a second reply for the same statement is rejected instead of creating a second debit.
  4. The settlement file (or, for shipping, the carrier invoice) is the source of truth. Reconciliation creates the liability and posts a correcting transaction rather than editing the original row.
  5. Reverse inside the NACHA window. After it closes, issue a new credit.

Recommended state handling

PENDING ├─→ SUCCESS (acknowledgment received) └─→ OUTCOME_UNKNOWN (timeout / no response) └─→ RECONCILING (settlement match runs) ├─→ MATCHED └─→ UNMATCHED → create liability record → REVERSED or REFUNDED

PENDING moves to SUCCESS on acknowledgment, or to OUTCOME_UNKNOWN on timeout. OUTCOME_UNKNOWN goes to RECONCILING, which ends in MATCHED or UNMATCHED. UNMATCHED creates a liability record, which is then REVERSED or REFUNDED.

The original payment is never set to REVERSED; only the new liability record is.

In ACH, acknowledgment is not final: an accepted debit can still be returned days later (for example, R01 for insufficient funds). Returns are a separate flow and outside the scope of this note.

Mapping to label purchase

Buying a carrier shipping label carries the same risk: the carrier can create, and later bill, a label even when our response is lost. The same rules apply:

  • Treat timeouts as OUTCOME_UNKNOWN, not FAILED.
  • Send a stable idempotency key across retries where the carrier’s API supports one.
  • Put the request ID in the shipment’s reference field, so each charge on the invoice can be matched back to a request.
  • Use the carrier invoice as the source of truth.
  • Post a correcting transaction for unmatched charges instead of changing the original purchase.
  • Place the label purchase at the saga pivot. Earlier steps can be compensated; later steps are retry-only or reconciled.

Closing

Every payment or money-adjacent design should start from the ambiguous case, not the happy path. The happy path is the one that already works.
